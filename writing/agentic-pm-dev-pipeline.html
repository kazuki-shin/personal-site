How I Shipped 25,000 Lines of Code in 3 Days With Zero Manual Coding

An agentic PM + dev pipeline that turns product decisions into deployed features — without a human writing a single line.

Last week I shipped 25,000 lines of production code across 39 tickets in three days. I didn't write a single line myself. Not because I couldn't, but because the bottleneck in software has shifted. Writing code is now the easiest part of building a product. The hard part is deciding what to build, specifying it precisely enough that a machine can execute, and reviewing the output. I built a pipeline that attacks this new bottleneck directly — a two-session architecture where one AI acts as my PM and another acts as my engineering team, connected by a project management tool that serves as the handoff layer.

The architecture

The system runs as two separate AI sessions with completely different roles, connected through Linear as the single source of truth. On one side is the PM session — an interactive conversation with Claude Code where I discuss product direction, debate UX trade-offs, and work through the shape of features. This session doesn't write code. It writes tickets: detailed specs with file paths, acceptance criteria, and dependency chains, pushed directly into Linear. On the other side is the dev session — an autonomous agent running Cline in kanban mode that reads tickets from Linear, spawns sub-agents in isolated git worktrees, builds features in parallel, runs its own code review, and ships pull requests. I never touch the dev session directly. It just watches the board and works.

The critical insight is the separation. The PM session holds the full product context — user research, design rationale, system architecture — without being polluted by implementation details. The dev session holds the full codebase context without being distracted by product debates. Linear sits between them as a clean interface: structured data in, structured data out. My role collapses to two things: I am the product owner who shapes decisions in the PM session, and I am the QA reviewer who approves pull requests from the dev session. One human, two functions, an entire engineering pipeline between them.

What this looks like in practice

The three days followed a natural arc. Day one was infrastructure and integrations — the kind of foundational work that has to happen before anything user-facing can ship. The PM session and I mapped out the system architecture, identified which third-party services needed to be wired up, and wrote tickets for each integration endpoint. The dev agents picked them off the board and built them in parallel across isolated worktrees. By end of day, the backend skeleton was standing.

Day two was stabilization and release. The PM session triaged bugs that surfaced from day one's rapid build, prioritized them by severity, and wrote fix tickets with exact file paths and line numbers where the problems lived. The dev agents turned those around fast because the specs were precise — no ambiguity, no back-and-forth. We shipped a working release by evening.

Day three is where the pipeline really showed its leverage. Our team had accumulated a batch of product feedback — feature requests, UX complaints, workflow gaps. I sat with the PM session for about an hour, working through the feedback and designing a new UX architecture to address it. The PM session then decomposed that architecture into 18 tickets with dependency chains, pushed them all to Linear, and the dev agents started executing immediately. Two parallel tracks ran simultaneously: one building the voice and configuration features, another building a new UI dashboard. The biggest single deliverable was a 1,187-line slide-over panel — I described what it should do in the ticket, and the agent built the entire thing. The dependency chaining meant that when one task finished, its downstream tasks auto-started without any human intervention.

What I learned

Ticket quality determines agent quality. This is the single most important lesson. The dev agents that produced clean, correct code on the first pass were the ones that received tickets with specific file paths, line numbers pointing to relevant existing code, and unambiguous acceptance criteria. The agents that struggled got vague tickets. If you're running a pipeline like this, spend 80% of your PM time on the specs. The writing is the work.

Dependency chaining is the multiplier that makes this more than a parlor trick. Without it, tasks run serially — each one waiting for a human to notice the previous one finished and manually assign the next. With dependency chains defined in Linear, two tracks can execute simultaneously and downstream tasks auto-start the moment their predecessors complete. The throughput difference between serial and parallel execution across 18 tickets is the difference between a day and a week.

Keep individual tasks under roughly 500 lines of code. Long-running agents accumulate context until they start to degrade — hallucinating function signatures, losing track of the file they're editing, repeating work they already did. The 1,187-line slide-over panel was at the absolute upper limit of what a single agent pass could handle cleanly. Smaller, well-scoped tasks produce dramatically more reliable output.

Separating PM and dev into distinct sessions is not just an organizational preference — it's architecturally necessary. When I tried running both in the same context early on, implementation details crowded out product thinking. The PM session would start suggesting code patterns instead of debating whether the feature was right. The dev session would start questioning product decisions instead of building. Separate contexts mean each session can go deep on its own concerns without interference.

Automate the handoff. The gap between "PM creates ticket" and "dev picks it up" is the weakest link in the entire pipeline. Every manual step in that gap — copying descriptions, reformatting specs, tagging priorities — degrades information and adds latency. The PM session writes directly to Linear's API. The dev session reads directly from Linear's API. No human in the middle means no information loss in the middle.

The bottleneck has moved. Writing code is now the cheapest, fastest part of building software. The hard part is knowing what to build, specifying it precisely enough that an agent can execute without ambiguity, and reviewing the result with enough taste to catch what the machine got wrong. The role of the founder-engineer is becoming the role of the founder-PM — and the agents are the engineering team.
